# Every way `khora-codegen-llvm`'s lowering can refuse a program.
#
# `scripts/check-backend-rules.sh` fails when this list and the code disagree.
# The list is not documentation -- it is the place a question gets asked, once
# per message: **can a program that passes `khora check` reach this?**
#
#   - If it can, the rule is a *language* rule and belongs in `khora-types`,
#     because the editor publishes what the checker says and nothing from here.
#     The backend then keeps its copy as an assertion about what reaches it.
#   - If it cannot, it is a statement about the compiler -- an operation the
#     backend does not implement, a shape the checker should already have
#     refused -- and belongs exactly where it is.
#
# Two rules failed that question and have moved: raising a type no declaration
# names, and an integer literal wider than an `Int`. Both type-checked cleanly
# and were refused at build time, which no editor could show.
#
# The two inline-layout rules were added by the commit that let variants share
# their slots and were never classified, so this check has been failing on
# `main`. Both are the second kind. `{ty}` has no inline layout is reached only
# where the lowering has already decided a value is held inline and
# `unboxed_type` then disagrees, which is the layout decision contradicting
# itself rather than anything a program can express; `{label}` was not given
# says so in the comment directly above it -- the checker refuses a literal
# naming neither every field nor a base, so there is nothing to read.
#
# Nine more became visible when the extractor learned to read a `.fail(` whose
# message wraps onto its own line -- see `check-backend-rules.sh`. Seven are
# below. Two are **not**, because they are the first kind and listing them here
# would assert something false:
#
# Both have since moved into `khora-types`, which is where a refusal a passing
# program can reach belongs, and the backend keeps its copies -- which is why
# both messages are listed below. The refutable `let` gained something in the
# move: the checker has the witness search in front of it, so it names the case
# that is not covered, where the backend only said one existed.
#
# `assert` outside a test was the other, and moved with it --
# `khora-types`'s `assert_outside_a_test_errors` reports it at the call, in the
# author's own file, where it used to arrive against `std/clock_native.kh:4`.
# The backend keeps its refusal, which is why the message is listed below.
# Roadmap 16.
#
# Two of the seven are worth a second look even though they are the right kind
# here. "only a named function or a constructor can be called; there are no
# function values until closures land" describes a language without closures,
# and closures landed. "`Ord::cmp` produces an `Ordering`" reads as a rule
# about a user's impl rather than as a statement about what reached the
# backend.
#
# Everything below has been read and is the second kind. Most say so in their
# own words: "is not an operation the backend knows", "which is a compiler
# bug", "has no machine type". The arity and shape checks are the checker's job
# and are duplicated here because lowering cannot proceed without the answer --
# a redundant check is the right shape for that, and a *sole* check is not.
